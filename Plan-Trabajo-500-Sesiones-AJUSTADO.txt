1.2 Por que no funciona con 500 sesiones

El problema es simple: tu server-simple.ts lanza UN solo proceso
Node.js. Ese proceso tiene el array sessions[] en memoria con las 97
conexiones WebSocket de Baileys. Node.js es single-threaded: no importa
que tengas 20 cores, un proceso solo usa 1 core (mas algo de garbage
collection en otro). Los otros 19 cores estan ociosos.

Tu intento con PM2 cluster fallo porque: en cluster mode, PM2 crea
copias del proceso. Cada copia tiene su PROPIO array sessions[] vacio.
Si el proceso A inicializa la sesion 5, el proceso B no puede acceder a
ella porque la memoria NO se comparte entre procesos. Es una limitacion
de como funciona Node.js, no un bug.

1.3 La solucion para tu caso

Con 20 cores y 94 GB RAM, tu maquina puede manejar 500+ sesiones SIN
comprar nada mas. La clave es lanzar 8 procesos Node.js con PM2 en modo
FORK (no cluster), cada uno en su propio puerto, cada uno dueno de ~60
sesiones. Redis coordina quien tiene que sesion.

2.2 Flujo de un Mensaje (paso a paso)

Ejemplo: un cliente del frontend quiere enviar un mensaje por la sesion
WhatsApp #45.

1.  El frontend hace POST /api/messages con sessionId=45 al dominio
    backend

2.  Nginx recibe el request y lo pasa al proceso Gateway (puerto 3001)

3.  El Gateway consulta Redis: HGET sessions:registry 45 -> responde
    'node-3:3004'

4.  El Gateway hace HTTP POST interno a
    http://localhost:3004/internal/send

5.  El proceso node-3 (puerto 3004) tiene la sesion 45 en su array
    sessions[]

6.  node-3 llama a Baileys sendMessage() y responde al Gateway

7.  El Gateway responde al frontend con el resultado

Latencia adicional del routing: ~5-10ms. Imperceptible para el usuario.

3. ARCHIVOS: QUE CREAR Y QUE MODIFICAR

3.1 Archivos NUEVOS a crear (7 archivos)

  ---------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  Archivo                      Que hace
  libs/sessionRegistry.ts      Registra en Redis que proceso tiene que sesion. Metodos: register(sessionId, nodeId), lookup(sessionId) -> nodeId, unregister(sessionId), getNodeSessions(nodeId) -> [ids]
  libs/heartbeat.ts            Cada proceso reporta 'estoy vivo' a Redis cada 10s con TTL de 30s. Si no renueva, Redis lo expira y el watchdog sabe que murio
  libs/watchdog.ts             Corre en node-1. Cada 30s escanea sesiones huerfanas (su nodo no tiene heartbeat). Las reasigna al nodo con menos carga
  libs/interProcessRouter.ts   Cuando GetWhatsappWbot no encuentra la sesion local, consulta Redis y hace HTTP POST a http://localhost:{puerto}/internal/... del proceso correcto
  routes/internal.ts           Endpoints internos: POST /internal/send, POST /internal/session/:id/status, POST /internal/session/:id/restart. Solo accesibles desde localhost
  server-distributed.ts        Nuevo entry point. Igual que server-simple.ts pero: lee NODE_ID y PORT de env vars, solo inicia sesiones asignadas a este nodo, activa heartbeat y registry
  libs/stagedConnection.ts     Inicia sesiones en batches de 20 con delay de 3s entre batches. Evita saturar CPU y rate-limit de WhatsApp al arrancar
  ---------------------------- ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------

Tu Nginx actual apunta a localhost:3001. Cambiarlo a un upstream con los
8 puertos y ip_hash para sticky sessions de Socket.IO:

-   upstream backend { ip_hash; server 127.0.0.1:3001; server
    127.0.0.1:3002; ... server 127.0.0.1:3008; }

-   La ruta /api/* y /socket.io/* apunta al upstream 'backend'

-   ip_hash asegura que un cliente siempre va al mismo proceso
    (necesario para Socket.IO polling fallback)

6.2 Que pasa si un proceso muere

1.  Proceso node-3 (puerto 3004) hace crash o se queda sin memoria

2.  Su heartbeat 'nodes:heartbeat:node-3' expira en 30 segundos (Redis
    lo borra solo)

3.  El watchdog (corriendo en node-1) detecta que node-3 no tiene
    heartbeat

4.  Busca en sessions:registry todas las sesiones de node-3 (ej: 45, 78,
    102...)

5.  Las reasigna al nodo con menos sesiones: HSET sessions:registry 45
    'node-5:3006'

6.  Llama POST http://localhost:3006/internal/session/45/restart

7.  node-5 lee el auth state de Redis (sessions:45:creds) y reconecta.
    Las credenciales ya estan en Redis, no se perdieron

Tiempo total de recuperacion: <30 segundos. Automatico, sin
intervencion.

7. PROXIES: POR QUE Y COMO

7.1 El problema de la IP unica

Tu VM de Contabo tiene 1 IP publica. WhatsApp ve 500 conexiones
WebSocket desde esa misma IP. Eso es una senal inequivoca de
automatizacion. Un usuario normal tiene 1 WhatsApp por IP.

7.2 Como funcionan los proxies

Un proxy es un servidor intermediario. Tu proceso se conecta a WhatsApp,
pero la conexion sale por el proxy, asi que WhatsApp ve la IP del proxy,
no la tuya.

-   Sin proxy: Tu VM (IP 1.2.3.4) -> WhatsApp. WhatsApp ve: 500
    conexiones desde 1.2.3.4

-   Con proxy: Tu VM -> Proxy (IP 5.6.7.8) -> WhatsApp. WhatsApp ve: 25
    conexiones desde 5.6.7.8

-   Con 20 proxies: 500 sesiones / 20 proxies = 25 sesiones por IP.
    Normal y seguro.

7.3 No instalas nada en tu servidor

Los proxies son un servicio externo que contratas. Te dan una lista de
IPs con usuario:password. Solo agregas 1 linea de codigo por sesion en
Baileys:

-   npm install https-proxy-agent (una vez)

-   En initWASocket, agregar: agent: new
    HttpsProxyAgent('http://user:pass@proxy-ip:port')

-   Redis guarda que proxy tiene cada sesion: HSET sessions:proxies 45
    'proxy-7'
